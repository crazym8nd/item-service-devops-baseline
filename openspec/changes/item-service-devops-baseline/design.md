## Context

Репозиторий пустой — проект создаётся с нуля как тестовое задание на позицию
Junior DevOps-инженера (см. `proposal.md` — Why). Ограничение по времени:
~4 часа. Нужно продемонстрировать конкретные DevOps-навыки из требований
вакансии (скриптинг, Docker, CI/CD, мониторинг), не уходя в
переусложнённую distributed-архитектуру.

## Goals / Non-Goals

**Goals:**
- Реалистичный, но маленький Spring Boot сервис как носитель для
  DevOps-артефактов.
- Все обязательные пункты задания (Dockerfile+compose, GitHub Actions,
  backup-скрипт, README) реализованы работоспособно.
- Дополнительно показать понимание production best practices через
  Flyway-миграции, run-once контейнер и observability-стек
  (Prometheus/Grafana/Loki/Alloy + postgres_exporter), на котором целиком
  построены мониторинг и алертинг (без самописного скрипта проверки
  здоровья — см. решение 7).
- Каждое архитектурное решение объяснено в README, включая то, что не стали
  делать и почему (Vault, шифрование бэкапов, TLS к БД).

**Non-Goals:**
- Kafka, ShardingSphere, шардирование, Kubernetes, Keycloak, MinIO, Tempo —
  не входят в скоуп (другой класс задач, другой уровень вакансии).
- Push Docker-образа в container registry из CI — не обязателен по условию
  задания, документируется как опциональный шаг.
- Реальная интеграция с HashiCorp Vault — только TODO с конкретикой в README.
- Инкрементальные бэкапы — только TODO в README, реализован full backup.
- Шифрование бэкапов (gpg/openssl) — только TODO в README.

## Decisions

### 1. Один REST-эндпоинт, минимальная сущность `Item{id, name}`
Обсуждались варианты: полный CRUD vs. только create. Выбран минимальный
набор — один `POST /api/items` — потому что цель сервиса не демонстрация
Spring-паттернов, а создание реальных данных в БД для бэкапа и реального
`/actuator/health`. Полный CRUD не добавляет ценности для оценки
DevOps-навыков и тратит время бюджета задания.

### 2. Схема БД через Flyway, а не Hibernate `ddl-auto=update`
Alternative: `ddl-auto=update` — проще для написания, но не соответствует
production-практике (неконтролируемые, недетерминированные изменения схемы).
Flyway с `ddl-auto=validate` даёт версионированную, воспроизводимую схему и
позволяет продемонстрировать паттерн run-once миграции как отдельного шага
жизненного цикла деплоя (см. решение 3).

### 3. `migrate` как отдельный run-once сервис в Compose (образ `flyway/flyway`)
Идея позаимствована из практики разделения "долгоживущих" и "разовых"
контейнеров (наблюдение из смежного учебного репозитория с шардированием,
без переноса самого шардирования). `flyway/flyway:11` — официальный образ,
версия зафиксирована по совместимости с Flyway 11.x, которым управляет
Spring Boot 3.5.10 (версия из reference-проекта),
не требует добавления Flyway как runtime-зависимости в само приложение
образа (хотя `flyway-core` всё равно нужен в classpath приложения для
`spring-boot-starter-flyway`-интеграции при локальном запуске без Docker,
если такой сценарий понадобится). `app` стартует по
`depends_on: migrate: condition: service_completed_successfully` —
Docker Compose нативно поддерживает такое условие, не требуется
самодельный wait-script.

Альтернатива — Flyway внутри Spring Boot при старте `app` — была бы проще,
но теряет демонстрацию идеи "run-once инфраструктурного шага", которую
явно попросил показать заказчик тестового.

### 4. Тесты — один `@SpringBootTest` на Testcontainers, без unit-тестов
Explicit decision пользователя: сервис — по сути заглушка для
DevOps-артефактов, юнит-тесты избыточны. Один интеграционный тест
покрывает три сценария (context loads, create success, validation failure)
и попутно доказывает, что миграции и JPA-маппинг согласованы. Docker
доступен в GitHub Actions `ubuntu-latest` из коробки, поэтому Testcontainers
в CI работает без дополнительной настройки (DinD/socket mounting не
требуется).

### 5. CI без push образа в registry
Задание требует только "сборка образа" в пайплайне, не публикацию. Push в
GHCR требует `permissions: packages: write` и решения о видимости пакета —
это точка, где легко занять чужие права доступа репозитория без
необходимости. Решение: `docker build` без `docker push`, инструкция по
добавлению push — в README как опциональный шаг для читателя.

### 6. `backup.sh`: full backup + SHA256 + gzip-integrity, retention 7 дней
Best practice для ежедневных бэкапов небольшого сервиса — баланс между
надёжностью восстановления (неделя истории) и местом на диске. SHA256
считается сразу после создания дампа и хранится рядом (`<file>.sha256`) —
это дёшево по времени реализации и обнаруживает как повреждение при записи,
так и последующую порчу/подмену файла. Инкрементальные бэкапы (WAL-archiving
/ `pg_basebackup` + continuous archiving) сознательно не реализуются в этом
задании — помечены как TODO, поскольку требуют настройки WAL-уровня и
отдельного retention-механизма, что не укладывается в бюджет времени.

### 7. Самописный healthcheck-скрипт исключён — мониторинг только на экспортерах
Explicit decision пользователя: отдельный `healthcheck.sh` не делаем.
Мониторинг и алертинг полностью строятся на двух прямых (whitebox)
экспортерах observability-стека:
- `app` отдаёт метрики через `/actuator/prometheus` → `up{job="app"}` —
  сигнал «приложение не отвечает».
- `postgres_exporter` подключается к `db` напрямую через SQL → `pg_up{job="postgres"}`
  — сигнал «БД недоступна».

Обоснование: самописный скрипт дублировал бы сигнал, который уже дают
экспортеры, добавлял бы ещё один канал алертинга с риском спама при
флаппинге (скрипт по cron без анти-flapping окна) и не давал бы
диагностики. Два экспортера покрывают оба нужных сигнала с анти-flapping
через `for: 1m` в Grafana Alert Rules — это реалистичный production-подход
и прямое соответствие требованию вакансии «настраивать мониторинг: правила».
Отступление от буквального текста задания (там упомянут health-check скрипт)
зафиксировано как осознанный trade-off, см. Risks.

### 8. Observability-стек — отдельный compose-файл
Минимальный набор: Prometheus + Grafana + Loki + Alloy (текущая
рекомендация Grafana вместо устаревающего Promtail) + postgres_exporter.
Версии образов зафиксированы по проверенному reference-проекту
(`prom/prometheus:v3.7.1`, `grafana/grafana:12.3.1`, `grafana/loki:3.6.3`,
`grafana/alloy:v1.12.2`, `prometheuscommunity/postgres-exporter:v0.18.1`),
а не `latest` — воспроизводимость и отсутствие сюрпризов при обновлении.
Не Loki/Tempo/Alloy full stack с трейсингом — трейсинг не требуется
заданием и не входит в must-have вакансии. Alloy настроен только на сбор
Docker stdout контейнеров `app`/`db`/`migrate` — без bind-mount хостовых
файлов логов `backup.sh` (скрипт не запускается в Docker, читается
человеком напрямую из файла лога на хосте).

Мониторинг строится на прямых источниках метрик (whitebox), без blackbox
exporter:
- `app` отдаёт метрики через `/actuator/prometheus` → `up{job="app"}` —
  сигнал «приложение не отвечает» (процесс упал/завис).
- `postgres_exporter` подключается к `db` напрямую через SQL и отдаёт
  метрики PostgreSQL → `pg_up{job="postgres"}` — сигнал «БД недоступна».
  (Пример конфигурации postgres_exporter взят из смежного учебного
  репозитория: образ `prometheuscommunity/postgres-exporter`, переменная
  `DATA_SOURCE_NAME=postgresql://user:pass@db:5432/db?sslmode=disable`,
  healthcheck на `wget --spider http://localhost:9187/metrics`.)

Почему прямые экспортеры, а не blackbox exporter:

1. **Whitebox даёт диагностику, blackbox — только факт.** Blackbox
   exporter проверяет систему снаружи, как внешний пользователь: он видит
   только «отвечает / не отвечает» и не знает причину. Прямые экспортеры
   отдают внутреннее состояние: метрики JVM и HTTP-запросов приложения,
   активные соединения и deadlocks БД. Для observability (а не просто
   uptime-мониторинга) важнее именно whitebox — он позволяет ответить на
   вопрос «почему», а не только «что упало».
2. **Прямой сигнал о БД точнее косвенного.** `pg_up` от postgres_exporter
   получен через SQL-подключение к самой БД — это прямое подтверждение
   доступности PostgreSQL. Blackbox через `/actuator/health` даёт косвенный
   сигнал (health вернул DOWN), который не различает причину: упала БД,
   не прошла миграция, закончился диск. Прямой экспортер локализует
   проблему без дополнительного расследования.
3. **Нет дублирования ролей.** Blackbox exporter проверял бы ровно то,
   что уже покрыто двумя прямыми экспортерами (`up` приложения и `pg_up`
   БД), — добавлять его значило бы проверять одно и то же в двух местах
   без новой информации.
4. **Меньше движущихся частей.** Blackbox exporter — это ещё один
   контейнер, ещё один scrape target и ещё одна точка отказа в
   конфигурации. Два прямых таргета (`app` и `postgres-exporter`) уже
   покрывают оба сигнала, нужных для алертинга.
5. **Соответствие production-практике.** В реальных системах PostgreSQL
   мониторят через postgres_exporter (метрики + доступность), а blackbox
   применяют точечно — для внешних сервисов, которые не отдают метрик
   (третьи стороны, публичные эндпоинты). Таких сервисов в этом задании
   нет.
6. **Богатство метрик для дашборда.** postgres_exporter даёт метрики для
   Grafana-дашборда (активные соединения, deadlocks, cache hit ratio) —
   это демонстрирует больше навыков, чем одна `probe_success`.

### 9. Секреты — `.env` + `.gitignore`, Vault — только TODO
Поднять Vault в `dev`-режиме тривиально, но интеграция с приложением
(`spring-cloud-vault-config`, bootstrap-конфигурация, auth-метод,
координация порядка старта `vault` → seed → `app`) — отдельный кусок
работы с реальным риском не уложиться в бюджет времени и снизить
работоспособность уже готового стека. Решение: секреты через `.env` (не
коммитится, права на файл рекомендуется выставлять 600 — упоминается в
README), Vault — предметный TODO с указанием конкретных компонентов
(`spring-cloud-vault-config`, KV v2 secrets engine, AppRole auth method).

## Risks / Trade-offs

- [Один Telegram-бот, единственный канал алертинга] → если Grafana
  недоступна (сам стек observability упал), алертов не будет вообще.
  Митигация: упомянуть в README как известное ограничение; для продакшена
  — TODO на резервный канал (например, внешний uptime-провайдер).
- [Отступление от буквального текста задания: health-check скрипт не
  реализуется] → задание упоминает «скрипт проверки здоровья с
  уведомлением», но по решению пользователя мониторинг и алертинг целиком
  строятся на observability-стеке (два экспортера + Grafana Alerting).
  Митигация: решение явно задокументировано в README с обоснованием
  (whitebox-диагностика, анти-flapping, отсутствие дублирования сигналов).
- [Single point of failure: одна БД без реплики] → потеря volume `db` =
  потеря всех данных между бэкапами. Митигация: ежедневный `backup.sh` +
  ротация; для продакшена — TODO на streaming replication.
- [`.env` с открытым паролем на диске] → компрометация хоста раскрывает
  секрет без аудита доступа и без ротации. Митигация: файловые права,
  явный TODO на Vault.
- [Testcontainers в CI требует Docker-in-Docker на раннере] → на
  `ubuntu-latest` GitHub-хостed раннере Docker доступен из коробки, риск
  минимален; но на self-hosted раннерах без Docker тест не пройдёт —
  упомянуть в README как допущение по CI-среде.
- [Ротация бэкапов по `mtime`] → если файловая система не хранит mtime
  корректно (редкий edge case) или системные часы хоста смещены, ротация
  может ошибочно удалить свежий или не удалить старый бэкап. Митигация:
  использование имени файла с timestamp как дополнительного независимого
  источника правды при необходимости (не в скоупе этой версии).

## Migration Plan

Новый проект, миграция не требуется. Порядок первого запуска: `git init` →
скопировать `.env.example` в `.env` → `docker compose up` (база стек) →
`docker compose -f docker-compose.yml -f
docker-compose.observability.yml up` (observability-стек, обязательная часть
поставки) → настроить Telegram Bot Token и Contact Point в Grafana
UI/provisioning для получения алертов.

Откат: `docker compose down -v` полностью уничтожает стек и данные (это
осознанно для тестового/дев-окружения; в README отдельно отмечается, что
для продакшена `-v` удалять volume нельзя без предварительного бэкапа).

### Публикация в личный GitHub пользователя

Это отдельная финальная задача, выполняемая агентом (не только описание для
человека), поскольку заказчик тестового явно просит: результат должен быть
залит в его личный GitHub, и должно быть подтверждено, что CI реально
проходит (не просто "выглядит правильно").

Шаги (выполняются после того, как весь код реализован и локально
провалидирован):
1. Проверить `gh auth status -h github.com` — авторизация должна быть на
   аккаунт пользователя (не на корпоративный GitLab), со скоупами минимум
   `repo` и `workflow` (без `workflow` пуш файлов `.github/workflows/**`
   будет отклонён GitHub).
2. Создать репозиторий через `gh repo create <owner>/<name> --private|--public
   --source=. --remote=origin` (имя и видимость — уточнить у пользователя
   перед выполнением, это первое реальное действие в его аккаунте).
3. Закоммитить весь реализованный код (`git add -A && git commit`) и
   запушить (`git push -u origin main`).
4. Дождаться завершения workflow: `gh run list` → `gh run watch <run-id>`
   (или `gh run list --workflow=ci.yml --limit 1` в цикле), убедиться, что
   статус `success`, а не `failure`/`cancelled`.
5. Если workflow упал — прочитать лог конкретного упавшего шага (`gh run
   view <run-id> --log-failed`), это триггерит обычный
   report→propose→approve→fix цикл, а не автоматический фикс вслепую.
6. Сообщить пользователю финальный URL репозитория и прямую ссылку на
   зелёный прогон Actions.

Явное несоответствие с обычной практикой: `gh repo create --source=.
--remote=origin` создаёт репозиторий *и* пушит текущий локальный `git`
history одной командой, поэтому шаги 2 и 3 по факту могут схлопнуться в одну
операцию — важно лишь чтобы к этому моменту весь код уже был закоммичен
локально.
